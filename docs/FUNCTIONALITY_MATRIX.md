# Vaultbreaker Functionality Matrix

The following matrix documents the verified state of all key features in Vaultbreaker based strictly on code inspection and test execution.

| Feature / Subsystem | Exists | Actually Works | Partially Works | Simulated | Broken | Code & Test Evidence |
|---|---|---|---|---|---|---|
| **Wallet Connection (MetaMask/HashPack)** | ❌ No | ❌ No | ❌ No | ❌ No | ❌ N/A | `wagmi`/`viem` in `package.json`, but zero wallet connection components or hooks in frontend source. |
| **Ledger Hardware CLI Protection** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `broker/src/ledger/keyring.ts`. Probes `wallet-cli --version` and runs CLI encrypt/decrypt. |
| **Ledger Seed Enclave Fallback** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | AES-256-GCM seed fallback in `keyring.ts`. Fully verified in Vitest (`broker.test.ts`). |
| **Agent Identity & Lifecycle Registry** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `broker/src/agent/registry.ts` & `/api/agents`. Authoritative state machine (`ACTIVE`, `SUSPENDED`, `REVOKED`), server-side auth gate in `/api/metered-service`, and UI management in `AgentsView.tsx`. Verified by 15 tests in `agent.test.ts`. |
| **Spend Policy Registration & Management** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `broker/src/policy/engine.ts` (`registerPolicy`, `updatePolicy`, `togglePolicy`) and `/api/policies`. Versioning, priority ordering, enabled toggling, and UI management in `PoliciesView.tsx`. |
| **Deterministic Policy Rule Evaluator** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `broker/src/policy/engine.ts` (`evaluatePolicies`). Precedence rule: explicit `DENY` overrides `ALLOW`. Priority sorting (`DESC`), applicability filtering, and explainable evaluation traces. Tested by 23 tests in `policy.test.ts`. |
| **Policy Velocity Rate Limiting** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented via sliding-window tracker (`velocityTracker`) in `broker/src/policy/engine.ts`. Enforces `maxCallsPerMinute` within 60s windows. Fully verified in Vitest. |
| **Policy UTC Time Window Enforcement** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `evaluatePolicies`. Enforces `allowedHoursUtc` (startHour, endHour) in UTC. Off-hours requests reject with `TIME_WINDOW_VIOLATION`. Verified in Vitest. |
| **Policy Blocked Actions & Resources** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Blacklist matching on `action` and `resource` paths. Rejects with `BLOCKED_ACTION` and `BLOCKED_RESOURCE`. Verified in Vitest. |
| **Policy Dry-Run Evaluation & UI Sandbox** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented at `POST /api/policies/evaluate` and interactive UI inspector in `PoliciesView.tsx`. Returns full trace without deducting tokens or invoking services. |
| **Zero-Deduction Guarantee on Policy Denial** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Integrated into Stage 6 of `POST /api/metered-service`. Budget tokens are NEVER decremented when a policy rejects a request. Verified by integration tests. |
| **Approval Lifecycle & State Machine** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `broker/src/approval/store.ts`. Deterministic 6-state machine (`PENDING`, `APPROVED`, `REJECTED`, `EXPIRED`, `CANCELLED`, `CONSUMED`), lazy UTC expiration, and query filters. Verified by 20 tests in `approval.test.ts`. |
| **Cryptographic Request Fingerprint (SHA-256)** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Computes SHA-256 over 9 execution parameters (`agentId`, `capId`, `serviceAddress`, `targetResource`, `requestedAction`, `requestedAmount`, `asset`, `policyId`, `policyVersion`). Enforces strict parameter matching on resumption. Verified in Vitest. |
| **Approval Escalation Gate (Zero Budget Deduction)** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Integrated into `POST /api/metered-service`. High-value requests return HTTP 202 `APPROVAL_REQUIRED` with pending approval record. Budget deduction is strictly zero. Verified in Vitest. |
| **Approval Resumption & Replay Prevention** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Resumption via `x-approval-id` header re-verifies all non-overridable checks, re-evaluates policy engine with `approvalVerified: true`, atomically marks approval `CONSUMED`, and decrements budget exactly once. Replay attempts reject with HTTP 403 `APPROVAL_ALREADY_CONSUMED`. Verified in Vitest. |
| **Operator Decision Authentication Boundary** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Middleware `verifyOperatorAuth` derives authoritative approver identity from token. Caller-supplied `approvedBy` in bodies is strictly ignored. Labeled as `DEVELOPMENT_DEMO_MODE` or `PRODUCTION_AUTH_ENFORCED`. Verified in Vitest. |
| **Operator Approval Inbox UI** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `app/src/components/ApprovalsView.tsx`. Status filter tabs, search, security boundary banner, live timers, approve confirmation modal, reject modal with required reason, and request inspection dossier. |
| **Hedera Consensus Service (HCS) Audit Trail** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Audit events for `APPROVAL_REQUESTED`, `APPROVAL_GRANTED`, `APPROVAL_REJECTED`, `APPROVAL_CANCELLED`, `APPROVAL_EXPIRED`, `APPROVAL_CONSUMED`, and `APPROVAL_EXECUTION_DENIED`. Recorded to HCS and queryable via `/api/audit-feed`. |
| **Capability Token Issuance** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `policy/engine.ts` (`issueCapability`) & `POST /api/capabilities/issue`. Verifies agent eligibility (`ACTIVE` required), validates action constraints and resource scopes, limits budget, embeds JWT claims, logs `CAPABILITY_ISSUED` to HCS. Tested in `capability.test.ts`. |
| **Capability Revocation (Broker Memory)** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `policy/engine.ts` (`revokeCapability`) & `POST /api/capabilities/revoke`. Sets `revoked=true` and `revokedAt`, immediately rejects future calls with HTTP 403 `CAPABILITY_REVOKED`, logs to HCS. Tested in `capability.test.ts`. |
| **Capability Revocation (On-Chain)** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `CapabilityRegistry.sol` (`revoke()`). Fully passing in Foundry (`test_SpendRevertsWhenRevoked`). |
| **Capability Expiry (TTL)** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Checked in broker `/api/metered-service` (returns HTTP 402 `CAPABILITY_EXPIRED`) & contract `spend()`. Fully tested in `capability.test.ts` & Foundry. |
| **Budget Enforcement (Broker Memory)** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `policy/engine.ts` (`decrementMemoryBudget`). Non-negative integer math, exact boundary testing, status transitions to `EXHAUSTED`, returns HTTP 402 `INSUFFICIENT_BUDGET`. Fully verified in Vitest & E2E simulation. |
| **Budget Enforcement (On-Chain EVM)** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented in `CapabilityRegistry.sol` (`spend()`). Passing 8/8 tests in Foundry. |
| **Broker ↔ On-Chain Synchronization** | ✅ Yes | ❌ No | ✅ Yes | ❌ No | ❌ No | `routes.ts` queries `registryContract.getCapability()`, but `/api/metered-service` does NOT send EVM txs during calls. |
| **x402 Micropayment Execution** | ✅ Yes | ✅ Yes | ❌ No | ❌ No | ❌ No | Implemented at `/api/metered-service`. Checks header `x-capability-token` and returns 402 on budget exhaustion. |
